## 1. Обзор

CodeTest — онлайн платформа для проверки кода. Пользователи создают задачи, загружают к ним наборы
тестов и отправляют исходный код решения, который исполняется в изолированной
песочнице и сравнивается с ожидаемым выводом.

Ключевое архитектурное решение: **сервис, принимающий HTTP-трафик, никогда не
исполняет недоверенный код**. Между приёмом сабмишна и его исполнением стоят два
асинхронных рубежа — Kafka и gRPC-очередь, — а само исполнение происходит в
контейнерах на отдельном Docker-демоне, у которого нет доступа ни к базе, ни к
объектному хранилищу, ни к сети.

Система состоит из трёх развёртываемых Go-сервисов, SPA-клиента и двух общих
библиотек. Взаимодействие идёт через три транспорта:

## 2. Компоненты

| Компонент | Путь | Реплик | Порты | Ответственность |
|---|---|---|---|---|
| **server** | `server/` | 1 | `8080` | AuthN/AuthZ, CRUD задач, загрузка тестов, приём сабмишнов, выдача статусов и вердиктов, прогон миграций БД при старте |
| **coordinator** | `checker/cmd/coordinator` | 1 | `50051` | Мост Kafka ↔ gRPC: читает `submissions`, держит очередь с арендой в памяти, обогащает задачу тест-кейсами, публикует вердикты в `submission-results` |
| **worker** | `checker/cmd/worker` | 3 | — | Забирает по одной задаче у координатора, исполняет решение в контейнере, возвращает вердикт |
| **client** | `client/` | — | `5173` (dev) | React 19 + Vite + TypeScript SPA, редактор на CodeMirror |
| **pkg/kafka** | `pkg/kafka` | — | — | Обёртки producer/consumer/admin, контракты сообщений |
| **pkg/storage** | `pkg/storage` | — | — | Клиент MinIO: объекты тестов и аватаров |

### Границы владения данными

Каждым хранилищем владеет ровно один сервис — прямого доступа «через границу» нет.

| Хранилище | Владелец | Кто ещё читает |
|---|---|---|
| PostgreSQL | server | никто |
| MinIO, бакет `tests` | server (запись) | coordinator (чтение) |
| MinIO, бакет `avatars` | server | браузер напрямую (публичный read) |
| Redis | coordinator | никто |

Воркеры не имеют доступа ни к одному хранилищу. Всё, что нужно для проверки —
код, язык и полный набор тест-кейсов, — приходит к ним внутри gRPC-сообщения.
Это держит процесс, исполняющий чужой код, свободным от любых учётных данных.

## 4. Жизненный цикл сабмишна

1. **Приём.** `POST /api/submit` валидирует запрос, сохраняет строку со статусом
   `pending` и синхронно публикует `SubmissionMessage` в топик `submissions`.
   HTTP-ответ возвращается сразу. Если публикация в Kafka не удалась, сабмишн
   немедленно помечается статусом `ERROR` — чтобы он не завис в `pending`
   навсегда.
2. **Постановка в очередь.** Coordinator читает `submissions` и кладёт задачу во
   внутреннюю очередь. **Offset коммитится сразу после постановки в очередь**, а
   не после получения вердикта — координатор не удерживает сообщение Kafka на
   время проверки. Последствия описаны в §11.
3. **Выдача воркеру.** Воркер в цикле дёргает `PullTask` (backoff 50 мс при
   пустой очереди). Очередь выдаёт задачу под аренду на 90 с и в этот же момент
   подтягивает тест-кейсы: сначала из Redis, при промахе — из MinIO с
   последующей записью в кеш.
4. **Исполнение.** Воркер поднимает контейнер, копирует туда исходник,
   при необходимости компилирует и прогоняет тесты по одному. Останавливается на
   первом непрошедшем тесте.
5. **Возврат вердикта.** Воркер вызывает `SubmitResult`. Координатор помечает
   запись выполненной (повторный вызов для той же записи отклоняется
   идемпотентно) и публикует `ResponseMessage` в `submission-results`.
6. **Применение вердикта.** Server читает `submission-results` в фоновой
   горутине и обновляет строку сабмишна.
7. **Доставка клиенту.** Клиент поллит `GET /api/submit?id=` раз в секунду, пока
   статус не выйдет из `pending`/`running`.

Если воркер упал между шагами 3 и 5, его аренда истекает через 90 с и задача
снова становится доступной для выдачи. Это единственный механизм ретраев в
очереди.

## 5. Транспорты и контракты

### 5.1 Kafka

Оба топика создаются идемпотентно при старте и `server`, и `coordinator`
(`kafka.EnsureTopics`) — это защищает от гонки, при которой консьюмер вступает в
группу раньше, чем топик реально существует на брокере, и получает 0 партиций.

| Топик | Партиций | RF | Producer | Consumer (group) |
|---|---|---|---|---|
| `submissions` | 1 | 1 | server | coordinator (`coordinator`) |
| `submission-results` | 1 | 1 | coordinator | server (`server-results-consumer`) |

Настройки producer: балансировка `Hash` по ключу, `RequiredAcks=all`,
синхронная запись. Ключ сообщения в обоих топиках — `submission_id`.

Настройки consumer: offset коммитится **вручную и только после успешной
обработки** — если handler вернул ошибку, offset не двигается и сообщение будет
доставлено повторно.

```go
// pkg/kafka/models.go

type SubmissionMessage struct {
    SubmissionID string `json:"submission_id"`
    TaskID       string `json:"task_id"`
    Code         string `json:"code"`
    Language     string `json:"language"`
}

type ResponseMessage struct {
    SubmissionID string `json:"submission_id"`
    Status       string `json:"status"`
    Output       string `json:"output"`
    Error        string `json:"error"`
}
```

### 5.2 gRPC

Схема: `checker/proto/judge.proto`, пакет `judge.v1`, сгенерированные стабы в
`checker/internal/grpc/judgepb`.

```protobuf
service Coordinator {
  rpc PullTask(PullTaskRequest) returns (PullTaskResponse);
  rpc SubmitResult(SubmitResultRequest) returns (SubmitResultResponse);
}
```

| Метод | Семантика |
|---|---|
| `PullTask` | Возвращает задачу под арендой либо пустой ответ, если очередь пуста. Воркер сам решает, когда просить работу — push со стороны координатора отсутствует. |
| `SubmitResult` | Принимает вердикт. `accepted=false` означает, что запись уже завершена (дубль) или неизвестна. |

`Task` несёт `submission_id`, `language`, `code` и полный список `TestCase`
(`number`, `input`, `expected_output`). `task_id` воркеру **не** передаётся —
он нужен только координатору, чтобы подтянуть тесты.

Статусы (`enum Status`): `OK`, `WA`, `RE`, `CE`, `TL`, `ML`, `ERROR`.

## 6. HTTP API

Базовый префикс — `/api`. Все ответы — JSON. Ошибки имеют единый вид:

```json
{ "error": "текст ошибки" }
```

### 6.1 Аутентификация

| Метод | Путь | JWT | Описание |
|---|---|:---:|---|
| `POST` | `/api/auth/register` | — | Регистрация. Возвращает `201` + access-токен, refresh-токен ставится в httpOnly cookie |
| `POST` | `/api/auth/login` | — | Вход. `200` + access-токен + cookie |
| `POST` | `/api/auth/refresh` | — | Обмен refresh-cookie на новый access-токен |
| `POST` | `/api/auth/logout` | — | Сброс refresh-cookie |
| `GET` | `/api/auth/me` | ✓ | Текущий пользователь |
| `PUT` | `/api/auth/profile` | ✓ | Смена username и/или пароля (при смене пароля обязателен `current_password`) |
| `POST` | `/api/auth/avatar` | ✓ | Загрузка аватара, `multipart/form-data`, поле `avatar` |

Коды ошибок: `400` — невалидный ввод, `401` — неверные креды или токен,
`409` — email/username занят.

### 6.2 Задачи

| Метод | Путь | JWT | Владелец | Описание |
|---|---|:---:|:---:|---|
| `GET` | `/api/tasks?limit=&offset=` | ✓ | — | Список задач. `limit` по умолчанию 10, допустимо 1..100; `offset` ≥ 0 |
| `POST` | `/api/tasks` | ✓ | — | Создать задачу |
| `GET` | `/api/tasks/{id}` | ✓ | — | Задача по UUID |
| `GET` | `/api/tasks/slug/{slug}` | ✓ | — | Задача по slug |
| `PUT` | `/api/tasks/{id}` | ✓ | ✓ | Изменить содержимое. Незаданные поля сохраняют значение; slug неизменяем |
| `DELETE` | `/api/tasks/{id}` | ✓ | ✗ | Удалить задачу (см. §11.2) |
| `POST` | `/api/tasks/{id}/tests` | ✓ | ✓ | Заменить набор тестов zip-архивом, `multipart/form-data`, поле `archive` |
| `POST` | `/api/tasks/{id}/tags` | ✓ | ✓ | Добавить теги к существующим |
| `PUT` | `/api/tasks/{id}/tags` | ✓ | ✓ | Заменить набор тегов целиком; пустой список очищает |
| `POST` | `/api/tasks/{id}/examples` | ✓ | ✓ | Заменить примеры ввода/вывода |

Столбец «Владелец» — требуется ли, чтобы вызывающий был создателем задачи.

Коды ошибок: `400` — невалидный ввод или архив, `403` — не создатель задачи,
`404` — задача не найдена, `409` — slug занят.

### 6.3 Сабмишны

| Метод | Путь | JWT | Описание |
|---|---|:---:|---|
| `POST` | `/api/submit` | ✓ | Отправить решение. Тело: `task_id`, `code`, `language` |
| `GET` | `/api/submit?id=` | ✓ | Статус и вердикт. Доступен только автору сабмишна |
| `GET` | `/api/submit/history?task_id=` | ✓ | История посылок текущего пользователя по задаче |

Коды ошибок: `400` — невалидный ввод или неподдерживаемый язык, `403` — чужой
сабмишн, `404` — сабмишн не найден.

### 6.4 Ограничения на ввод

| Сущность | Правило |
|---|---|
| Пароль | ≥ 8 символов |
| Username | ≥ 3 символов, приводится к нижнему регистру, уникален |
| Email | содержит `@` и `.`, нижний регистр, уникален |
| Аватар | ≤ 5 MiB, `image/jpeg`, `image/png` или `image/webp` |
| Slug задачи | нижний регистр, пробелы → дефисы, уникален |
| Сложность | `easy` \| `medium` \| `hard` |
| `time_limit_ms`, `memory_limit_mb` | > 0 |
| Тег | ≤ 50 символов после нормализации, дубли отбрасываются |
| Примеры | ≤ 3 на задачу; строки, пустые с обеих сторон, отбрасываются |
| Архив тестов | ≤ 50 MiB; ≤ 500 тестов; один файл ≤ 10 MiB (проверяется по заявленному размеру до распаковки — защита от zip-бомбы) |
| Имена в архиве | строго `test_NNN.in` / `test_NNN.out`; служебные записи macOS (`__MACOSX/`, `._*`, `.DS_Store`) игнорируются; `..` в пути отвергается |
| Язык | `python` \| `cpp` \| `go` |

Загрузка тестов имеет семантику **replace-all**: перед записью нового набора
старый удаляется целиком. При ошибке на середине выполняется best-effort
откат — чтобы не осталось смеси старых и новых тестов.

## 7. Модель данных

### 7.1 PostgreSQL

Миграции — `server/migrations/`, применяются автоматически при старте сервера
через `golang-migrate`. Путь к ним резолвится относительно рабочей директории
(`file://server/migrations`), поэтому сервер должен запускаться из корня
репозитория; в образе это обеспечено `WORKDIR /app` и копированием миграций.

```
   users                          tasks                      task_examples
┌──────────────┐             ┌──────────────────┐         ┌────────────────┐
│ id        PK │──┐       ┌─▶│ id            PK │◀───────<│ task_id     FK │
│ email     UQ │  │       │  │ slug          UQ │         │ example_input  │
│ username  UQ │  │       │  │ title            │         │ example_output │
│ password_hash│  │       │  │ statement        │         └────────────────┘
│ avatar_url   │  │       │  │ difficulty  ENUM │
│ created_at   │  │       │  │ time_limit_ms    │            tags
└──────────────┘  │       │  │ memory_limit_mb  │         ┌──────────────┐
                  │       │  │ created_by    FK │─┐    ┌─▶│ id        PK │
                  │       │  │ created_at       │ │    │  │ name      UQ │
                  │       │  │ updated_at       │ │    │  └──────────────┘
                  │       │  └──────────────────┘ │    │
                  │       │           ▲           │    │      task_tags
                  │       │           │           │    │  ┌────────────────┐
                  │       │           └───────────┼────┼─<│ task_id     FK │
                  │       │                       │    └─<│ tag_id      FK │
                  │       │                       │       │  PK(task,tag)  │
                  │       │  submissions          │       └────────────────┘
                  │       │┌──────────────────┐   │
                  │       ││ id            PK │   │
                  └───────┼┤ user_id       FK │   │
                          ││ task_id       FK │◀──┘
                          └┤ code             │
                           │ language         │
                           │ status           │
                           │ output           │
                           │ error            │
                           │ created_at       │
                           │ updated_at       │
                           └──────────────────┘
```

Все внешние ключи — `ON DELETE CASCADE`, кроме `tasks.created_by`, который
намеренно ограничивающий: пользователя нельзя удалить, пока за ним числятся
задачи.

Индексы: `tasks(difficulty)`, `tasks(created_by)`, `task_tags(tag_id)`,
`task_examples(task_id)`, `submissions(task_id)`, `submissions(user_id)`,
`submissions(status)`, `submissions(created_at DESC)`.

Статусы сабмишна: `pending` → `OK` \| `WA` \| `RE` \| `CE` \| `TL` \| `ML` \|
`ERROR`. Константа `running` объявлена в модели и учитывается клиентом при
поллинге, но **никогда не записывается в базу** — промежуточного состояния
«взято воркером» сейчас нет.

Запросы задач избегают проблемы N+1: теги и примеры подтягиваются на весь список
одним запросом с `WHERE ... = ANY($1)` и раскладываются по задачам в памяти.

### 7.2 MinIO

| Бакет | Доступ | Формат ключа | Содержимое |
|---|---|---|---|
| `codetest-tests` | приватный | `{taskID}/test{NNN}.{in,out}` | Тест-кейсы задач |
| `codetest-avatars` | публичный read | `{userID}` | Аватары, отдаются браузеру напрямую |

Номер теста в ключе пишется с паддингом до трёх знаков, но при чтении
распознаётся любое число знаков — задачи с ≥ 1000 тестов не теряются.
`ListTests` возвращает ошибку, если у какого-то номера есть только одна половина
пары: неполный набор лучше отвергнуть явно, чем судить по нему.

Публичный URL аватара строится через отдельный `MINIO_PUBLIC_ENDPOINT`: внутри
compose сервер ходит в MinIO по внутреннему адресу, а браузеру нужен адрес
опубликованного порта. К URL добавляется `?v={timestamp}` — объект всегда лежит
по одному и тому же ключу, и без этого браузер продолжал бы показывать старый
аватар.

### 7.3 Redis

Кеш тест-кейсов перед MinIO, целиком принадлежит координатору.

| Свойство | Значение |
|---|---|
| Ключ | `testcache:{taskID}` |
| Значение | JSON-массив `{n, i, o}` |
| TTL | отсутствует |
| Вытеснение | `maxmemory 256mb`, политика `allkeys-lru` |
| Персистентность | отключена (`--save ""`) |
| Поведение при ошибке | трактуется как промах кеша |

Кеш **best-effort**: недоступность Redis не ломает проверку, она просто идёт в
MinIO. Инвалидации нет — тесты считаются неизменяемыми после загрузки
(см. §11.2).

## 8. Исполнение недоверенного кода

Реализация — `checker/internal/worker/docker.go`, поверх Docker Engine API.
Воркеры работают с **отдельным Docker-демоном** (`dind` в compose), а не с
демоном хоста: `DOCKER_HOST=tcp://dind:2375`.

### 8.1 Поддерживаемые языки

| Язык | Образ | Компиляция | Запуск |
|---|---|---|---|
| `python` | `python:3.12-slim` | — | `python3 /tmp/solution.py` |
| `cpp` | `gcc:13` | `g++ -O2 -o /tmp/solution /tmp/solution.cpp` | `/tmp/solution` |
| `go` | `golang:1.23` | `go build -o /tmp/solution /tmp/solution.go` | `/tmp/solution` |

Для Go монтируется именованный том `codetest-go-build-cache` в
`/root/.cache/go-build`. Без него каждый сабмишн собирал бы стандартную
библиотеку с нуля, что может превысить таймаут компиляции.

Образы подгружаются в фоне при старте воркера (`WarmImages`). Блокировать старт
на этом нельзя: у изолированного демона нет кеша образов хоста, и первая
загрузка тянет более двух гигабайт. Одновременные запросы одного образа
разделяют одну загрузку, а не запускают параллельные.

### 8.2 Изоляция и лимиты

Один контейнер на сабмишн, команда `sleep infinity`; тесты гоняются как
отдельные `exec` внутри него.

| Ограничение | Значение | Механизм |
|---|---|---|
| Сеть | отсутствует | `NetworkMode: none` |
| Память | 256 MiB | `Memory` + `MemorySwap` равны, иначе своп удваивает фактический лимит |
| CPU | 1 vCPU | `NanoCPUs` |
| Процессы | 64 | `PidsLimit` — защита от fork-бомбы |
| Время на тест | 5 с | `timeout` **внутри** контейнера |
| Время компиляции | 40 с | то же |
| Файловая система | своя на контейнер | контейнер удаляется принудительно после сабмишна |

Лимит времени навязывается изнутри контейнера утилитой `timeout`, а не через
`context` снаружи: у Docker API нет прямого способа убить конкретный exec, и
полагаться на отмену контекста здесь было бы ненадёжно.

### 8.3 Определение вердикта

| Код возврата | Вердикт | Уточнение |
|---|---|---|
| `0`, вывод совпал | `OK` | сравнение после нормализации |
| `0`, вывод не совпал | `WA` | |
| `124` | `TL` | код `coreutils timeout` при убийстве по таймауту |
| `137` | `ML` | SIGKILL; эвристика — точнее без чтения cgroup-событий OOM не отличить от любого другого SIGKILL |
| прочее | `RE` | |
| ошибка компиляции | `CE` | |
| сбой инфраструктуры | `ERROR` | недоступен образ, не создалась песочница и т. п. |

Нормализация вывода перед сравнением: `\r\n` → `\n`, срезаются пробелы и табы в
конце каждой строки и пустые строки в конце вывода. Проверка останавливается на
первом непрошедшем тесте.

## 9. Аутентификация и авторизация

Схема — JWT, HS256, два независимых секрета.

| Токен | TTL по умолчанию | Переменная | Хранение |
|---|---|---|---|
| access | 15 минут | `JWT_ACCESS_TTL_MINUTES` | клиент, `localStorage` |
| refresh | 30 дней | `JWT_REFRESH_TTL_DAYS` | httpOnly cookie, `SameSite=Lax` |

`AuthMiddleware` разбирает заголовок `Authorization: Bearer`, валидирует
access-токен и кладёт `subject` (UUID пользователя) в контекст запроса.
Обработчики достают его через `auth.UserIDFromContext`.

Пароли хешируются `bcrypt` с `DefaultCost`.

Модель авторизации плоская: ролей нет. Право на изменение задачи определяется
единственным правилом — `tasks.created_by == user_id`; сабмишн виден только
своему автору.
