# Архитектура

## 1. Обзор

CodeTest — онлайн-судья: пользователи пишут условия задач, загружают наборы
тестов и отправляют исходный код, который проверяется асинхронно относительно
этих тестов. Система разбита на три развёртываемых юнита и две общие
библиотеки, взаимодействующие через три транспорта: REST (клиент-сервер),
Kafka (сервер → checker-подсистема) и gRPC (внутри checker-подсистемы,
pull-модель).

```
┌──────────┐   REST + JWT    ┌──────────────┐
│  Клиент  │ ───────────────▶│    Сервер    │── Postgres  (users, tasks, submissions, tags)
│ (React)  │◀─────────────── │ (go-chi API) │── MinIO     (тесты, аватары)
└──────────┘  поллинг вердикта└──────┬───▲───┘
                                     │   │
                        submissions  │   │ results
                                     ▼   │
                             ┌───────────────────┐
                             │       Kafka        │
                             │ submissions /       │
                             │ submission-results  │
                             └──────────┬───▲──────┘
                                        │   │
                            submissions │   │ results
                                        ▼   │
                             ┌────────────────────┐        gRPC (pull)       ┌─────────┐
                             │    Coordinator      │◀─────────────────────────│ Worker  │ x N
                             │ (очередь с арендой   │  PullTask / SubmitResult │(реплики)│
                             │  в памяти, состояние │─────────────────────────▶│         │
                             │  в Postgres не       │                          └─────────┘
                             │  хранится)           │
                             └────────────────────┘
```

Сервер никогда не исполняет недоверенный код сам. Он общается только с Kafka
и со своими собственными хранилищами. Всё исполнение решений происходит за
coordinator'ом, в процессах-воркерах, которые вообще не видят ни Postgres, ни
MinIO, ни клиента напрямую.

## 2. Сервисы

| Сервис | Путь | Рантайм | Ответственность |
|---|---|---|---|
| **server** | `server/` | Go, единый бинарник | AuthN/Z, CRUD задач, загрузка наборов тестов, приём сабмишнов, API статусов/вердиктов, прогон миграций БД при старте |
| **coordinator** | `checker/cmd/coordinator` | Go, единый бинарник, 1 реплика | Мост между Kafka и gRPC: читает `submissions`, держит очередь с арендой в памяти, отдаёт задачи воркерам по gRPC, публикует принятые результаты в `submission-results` |
| **worker** | `checker/cmd/worker` | Go, N реплик (`docker-compose.yml`: 3) | Забирает по одной задаче за раз у coordinator'а по gRPC, судит её, отправляет результат обратно |
| **client** | `client/` | React 19 + Vite + TS | SPA; общается только с REST API сервера, поллит статус сабмишна |
| **pkg/kafka** | `pkg/kafka` | общий Go-модуль | Обёртки producer/consumer/admin, контракты сообщений (`SubmissionMessage`, `ResponseMessage`) |
| **pkg/storage** | `pkg/storage` | общий Go-модуль | Клиент MinIO: объекты тестов, объекты аватаров |

Сервер и coordinator никогда не вызывают друг друга напрямую — только через
Kafka. Это значит, что каждый из них можно передеплоить или отмасштабировать
независимо, не теряя сабмишн, летящий в этот момент между ними (с оговорками
из §4).

## 3. Распределённая обработка сабмишнов

Судейство намеренно разбито на два уровня: **Kafka** отделяет сервер от
checker-подсистемы целиком; **gRPC pull** отделяет coordinator от
эластичного пула воркеров.

1. `POST /api/submit` сохраняет сабмишн (`status=pending`) и публикует
   `SubmissionMessage{submission_id, task_id, code, language}` в топик
   `submissions`. HTTP-запрос завершается сразу же.
2. **Coordinator** читает `submissions`, находит тесты задачи и кладёт job в
   очередь в памяти (`checker/internal/coordinator/queue.go`). Offset в Kafka
   коммитится сразу после постановки в очередь — coordinator не ждёт
   вердикта, чтобы подтвердить сообщение Kafka.
3. Каждый **воркер** в цикле опрашивает `PullTask` (backoff 50 мс при пустой
   очереди). Очередь выдаёт задачу под аренду на 30 с; фоновая уборка
   периодически убирает завершённые записи. Если воркер падает, его аренда
   просто истекает и задача снова становится доступной — это единственный
   механизм ретраев очереди, и он полностью в памяти (теряется при рестарте
   coordinator'а).
4. Воркер судит сабмишн и вызывает `SubmitResult`. Coordinator помечает
   запись в очереди как выполненную и republish'ит вердикт как
   `ResponseMessage` в `submission-results`. Повторный `SubmitResult` для уже
   завершённой записи отклоняется идемпотентно.
5. **Сервер** читает `submission-results` в фоновой горутине и обновляет
   строку сабмишна. Клиент поллит `GET /api/submit?id=` раз в секунду, пока
   статус не выйдет из `pending`/`running`.

**Текущее ограничение:** `Worker.judge()` (`checker/internal/worker/worker.go`)
— заглушка: она засыпает и безусловно возвращает `OK`. Реальное исполнение в
песочнице (контейнер под язык, шаг компиляции, лимиты ресурсов, честное
сравнение с ожидаемым выводом) пока не реализовано. Выше воркера ничего
менять не придётся, когда это появится: gRPC-контракт уже несёт `language`,
`code` и полный `test_cases` (вход + ожидаемый вывод) на каждую задачу.

## 4. Гарантии доставки (честный разбор)

- **Окно потери сабмишна:** если coordinator падает после того, как выдал
  задачу воркеру, но до того, как тот отчитался — задача теряется: она
  существует только в памяти coordinator'а, уже не в Kafka (offset
  закоммичен на шаге 2) и никогда не была в Postgres. С точки зрения клиента
  сабмишн навсегда зависает в `pending`.
- **At-least-once, не exactly-once:** консьюмер-группы Kafka вместе с
  очередью аренды могут при рестартах/партициях повторно доставить задачу;
  проверка идемпотентности в `Queue.Complete` защищает только от *дубля
  результата* для одной и той же записи, но не от повторной постановки того
  же сабмишна в очередь после рестарта coordinator'а (очередь намеренно не
  переживает рестарт — она осознанно не backed'ится базой данных).
- **Нет backpressure на воркерах:** воркеры busy-poll'ят; push/notify-пути
  нет, поэтому и холостая нагрузка на CPU воркера, и задержка результата
  масштабируются вместе с `pollInterval`.

Это осознанно принятые компромиссы под текущий масштаб проекта, а не
недосмотры, которые тихо обходятся стороной — любое изменение здесь
(например, персистентность очереди аренды) должно быть осознанным
архитектурным решением, а не фиксом бага.

## 5. Хранилища данных

| Хранилище | Кто использует | Содержимое |
|---|---|---|
| **PostgreSQL** | только server | `users`, `tasks`, `tags`/`task_tags`, `submissions`. Миграции в `server/migrations/`, применяются автоматически при старте сервера через `golang-migrate`. |
| **MinIO (бакет tests)** | server, через `pkg/storage` | Объекты тестов на задачу, формат ключа `{taskID}/test{NNN}.{in,out}`. Заполняется из zip-архива `test_NNN.in`/`test_NNN.out` (`POST /api/tasks/{id}/tests`), семантика replace-all. |
| **MinIO (бакет avatars)** | server, через `pkg/storage` | Изображения аватаров пользователей, отдаются с публичного эндпоинта, отдельного от приватного бакета с тестами. |

У checker-подсистемы (coordinator, worker) нет прямого доступа ни к базе, ни
к объектному хранилищу — содержимое тестов передаётся воркерам целиком по
gRPC внутри сообщения `Task`, а не запрашивается ими самостоятельно. Это
держит границу исполнения кода свободной от учётных данных хранилищ.

## 6. API

Все роуты под `/api/tasks` и `/api/submit` требуют JWT
(`Authorization: Bearer`), выданный через `/api/auth/login` и проверяемый
`authinternal.AuthMiddleware`.

| Эндпоинт | Auth | Описание |
|---|---|---|
| `POST /api/auth/register` | — | Создать аккаунт (опционально с загрузкой аватара) |
| `POST /api/auth/login` | — | Обменять креды на пару access/refresh токенов |
| `POST /api/auth/refresh` | — | Обновить access-токен |
| `POST /api/auth/logout` | — | Инвалидировать refresh-токен |
| `GET /api/tasks` | JWT | Список задач (с пагинацией) |
| `POST /api/tasks` | JWT | Создать задачу |
| `GET /api/tasks/{id}` | JWT | Получить задачу по ID |
| `GET /api/tasks/slug/{slug}` | JWT | Получить задачу по slug |
| `DELETE /api/tasks/{id}` | JWT | Удалить задачу (только владелец) |
| `POST /api/tasks/{id}/tests` | JWT | Заменить набор тестов задачи из zip-архива (только владелец) |
| `POST /api/tasks/{id}/tags` | JWT | Прикрепить теги к задаче |
| `POST /api/submit` | JWT | Отправить решение на проверку |
| `GET /api/submit?id=` | JWT | Получить текущий статус/вердикт сабмишна |
| `GET /api/submit/history` | JWT | Список сабмишнов пользователя по задаче |

## 7. Стек

- **Go 1.25** — server, coordinator, worker; `chi` (HTTP-роутинг), `pgx`
  (драйвер Postgres), `golang-migrate` (миграции схемы), клиент Kafka через
  `pkg/kafka`, gRPC через сгенерированные стабы `judgepb`.
- **PostgreSQL 16** — система хранения истины для пользователей, задач,
  сабмишнов.
- **Apache Kafka 3.8** — надёжный транспорт между сервером и
  checker-подсистемой; два топика, `submissions` и `submission-results`.
- **gRPC** — внутренний транспорт между coordinator'ом и воркерами; наружу
  из checker-подсистемы не выходит.
- **MinIO** — S3-совместимое объектное хранилище для тестов и аватаров.
- **React 19 + Vite + TypeScript** — SPA-клиент, редактор кода на CodeMirror
  для решений (Python/Go/C++/JavaScript).

## 8. Топология развёртывания

Описана в `docker-compose.yml`: `postgres`, `kafka`, `minio` (инфраструктура)
плюс `server`, `coordinator` и `worker` (реплики: 3) как сервисы приложения.
Порты наружу открывают только `server` и `coordinator` (`8080`, `50051`);
воркеры — чисто исходящие gRPC-клиенты и ничего не экспонируют.
